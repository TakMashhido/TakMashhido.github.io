A paper about a new physically unclonable function (PUF) has to report the same handful of numbers: uniformity, uniqueness, reliability, bit-aliasing, an identification error rate, some randomness tests, and how much error correction a key would need. Almost every group computes them with its own scripts, and the scripts quietly disagree. Some report uniqueness as twice the standard value. Some quote a false-acceptance rate of zero because none of their few hundred comparisons failed. Some run NIST tests on a few hundred bits, where the p-values mean nothing.

**PUFAnalytics** is my attempt to make that part of the work boring and correct. It is a Python package and a web app that give the same answers to the last digit. You can load measurements or simulate a population, get every standard metric with confidence intervals, and leave with a LaTeX table, figures and a script that reproduces it all. It accompanies our IEEE APCC 2025 paper.

**Try it:** [open the PUFAnalytics web app](https://koustav.isroot.in/PUFAnalytics/) and press **Explore a demo population**. Nothing is uploaded; it runs in your browser and works offline. The code is on [GitHub](https://github.com/TakMashhido/PUFAnalytics) under the MIT license.

![The PUFAnalytics overview for a simulated 64-stage Arbiter PUF: quality index 94, NIST 7 of 8 tests passed, mean BER 0.46%, and a radar chart of seven normalised scores](/images/blog/pufanalytics/overview.webp)

New to PUFs? [How a PUF works](/blog/how-a-puf-works/) explains the hardware, the four headline metrics and how PUFs are attacked. This post is about the tool: what each part does, how to use it, and how the numbers are computed.

## Two engines, one answer

PUFAnalytics exists twice. The **Python package** (`pip install`, NumPy only) suits scripts, notebooks, batch jobs and the command line. The **web app** is plain HTML, CSS and JavaScript modules with no framework and no build step; it suits exploring a data set, making figures and showing results to someone. Its analysis engine in `web/js/core/` is a line-by-line port of the Python modules, and it runs in a Web Worker so the page stays responsive during a 1,000-sample bootstrap.

<PaArchitecture />

Two decisions keep the engines in step:

- **One random number generator for both.** Simulators and the bootstrap draw from xoshiro128\*\*, seeded through SplitMix32, implemented identically in Python and JavaScript. Neither engine uses `Math.random()` or NumPy's generator.
- **A parity test in CI.** `tests/make_golden.py` writes reference values from Python into `web/tests/golden.json`, and `node web/tests/parity.test.mjs` requires the browser engine to reproduce all of them. That is over 2,400 checks across metrics, statistics, NIST tests and simulators.

**Your data stays with you.** The web app is a static site on GitHub Pages. Files are parsed and analysed on your machine and saved only in your browser's IndexedDB, and a service worker caches the app so it keeps working offline.

## The data model

Everything in PUFAnalytics works on one structure, `PUFDataset`: a block of **devices × measurements × bits**, plus an operating-condition label (such as `25C` or `85C`) for each read-out. Measurement 0 of each device is its **enrolment reference**. Every metric is one particular comparison inside this block:

<PaDataModel />

| Comparison | Metric | Ideal |
|---|---|---|
| Share of 1s in a device's reference | **Uniformity** | 50% |
| One bit position across all devices' references | **Bit-aliasing** | 50% at every position |
| Reference vs reference, over all device pairs | **Uniqueness** (inter-device distance) | 50% |
| A device's re-reads vs its own reference | **Reliability**, bit error rate (BER) | 100%, 0 |
| The same, split by condition label | **BER per operating condition** | as low as possible |

### Data formats

The importer accepts CSV, TXT, JSON and NumPy `.npy`. The richest layout is one row per read-out, with the response in binary or hex:

```text title="measurements.csv"
device,measurement,condition,response
chipA,0,25C,0xA3F1C29B7E4D0516
chipA,1,85C,0xA3F1C2997E4D0716
chipB,0,25C,0x5C0E3D64819BF2E9
```

Simpler layouts also work:

- one response per line (one device each);
- `device,response`, where repeated device rows are re-measurements;
- `device,measurement,response`;
- whitespace-separated bits;
- NumPy arrays shaped `(devices, bits)` or `(devices, measurements, bits)`.

Separators can be commas, semicolons, tabs or spaces, and `#` starts a comment. In auto mode a file is read as binary only if *every* response is made of 0s and 1s; otherwise it is hex, at 4 bits per digit. [Method notes: data formats](https://koustav.isroot.in/PUFAnalytics/#/docs/formats).

### 1. Data & simulation

This is where data comes in, either simulated or imported.

![The Data & simulation view: a simulator panel with model tabs (Arbiter/XOR, Feed-forward, Interpose, Ring oscillator, SRAM, DRAM, Ideal), population size, seed, model parameters and operating conditions, next to the import panel with a drop zone and a paste box](/images/blog/pufanalytics/data.webp)

**To simulate a population:**

1. Pick a model tab.
2. Set the **Devices**, **Response bits**, **Repeats / condition** and **Seed** fields. The dice button draws a random seed.
3. Set the model's own parameters, in the row below.
4. Add operating conditions with **+ Condition**, or pick one from **Presets**. Each condition has a label and a noise scale. The first read of the first condition is the enrolment.
5. Press **Generate & analyse**.

Seven models are built in:

| Model | What it simulates | Parameters (defaults) |
|---|---|---|
| **Arbiter / XOR** | Additive delay model: the response is the sign of a weighted sum of challenge-parity features; XOR of several chains | stages 64, XOR chains 1, noise σ 0.05 |
| **Feed-forward** | Arbiter PUF where intermediate arbiters set later challenge bits (non-linear) | stages 64, loops 1, noise 0.05 |
| **Interpose** | (x, y)-iPUF: an x-XOR arbiter's output is inserted mid-challenge of a y-XOR arbiter | stages 64, x 1, y 1, noise 0.05 |
| **Ring oscillator** | Pairs of oscillators compared by frequency, with process variation and a systematic gradient shared by all chips | process σ 1, noise 0.1, gradient 0, pairing neighbour/disjoint |
| **SRAM** | Power-up state of each cell from a fixed mismatch plus thermal noise | noise 0.1, cell bias 0 |
| **DRAM** | Retention: a cell reads 1 if it decays during the refresh pause; heat speeds decay | noise 0.1, threshold 0, temperature shift 0.3 |
| **Ideal** | Uniform random bits with independent flips: what "perfect" looks like at your sample size | flip probability 0.02 |

The Ideal model is more useful than it looks. With 32 devices, even a perfect PUF will not show exactly 50% uniqueness, and simulating an ideal population of the same size shows you how much scatter to expect. [Method notes: simulators](https://koustav.isroot.in/PUFAnalytics/#/docs/simulators).

**To import:**

1. Drop a file on the drop zone, or paste text into the box.
2. Give it a name and choose an encoding: **Auto-detect**, **Binary** or **Hexadecimal**.
3. Press **Import & analyse**.

**Load example text** fills the box with a valid sample, and **Accepted layouts** lists every format.

Below the two panels, every loaded data set has **Rename**, **CSV**, **JSON** and delete buttons. Under those are three pre-processing tools and a response explorer:

![Pre-processing tools (bit window, dark-bit masking with a maximum flip rate, device subset) above the response explorer, a bitmap of every device's enrolled response](/images/blog/pufanalytics/preprocess.webp)

The pre-processing tools never change the original. Each one creates a new, derived data set:

- **Bit window** keeps the bit positions from *From bit* up to, but not including, *To bit*. Use it, for example, to study the first 64 bits of a 128-bit response.
- **Dark-bit masking** drops bit positions whose flip rate across the population is above a threshold (default 0.05). This is the standard way to trade response length for reliability before key generation.
- **Device subset** keeps the first *N* devices. It is useful for checking how stable a metric is as the population grows.

The **response explorer** draws every device's bits as a bitmap. It has three modes: **Enrolment**, **Majority vote** (the bitwise majority of all reads) and **Stability map** (the flip rate of each cell). Stripes or columns in the enrolment view mean bias, and bright cells in the stability map show where the noise is.

In Python: `pa.simulate()`, `pa.PUFDataset.from_file()`, `PUFDataset.subset()` and `quality.bit_flip_rate()`.

### 2. Quality metrics

![The Quality metrics view: analysis settings (enrolment reference, bootstrap B, CI level, NIST alpha, bootstrap seed) above a summary table of uniformity, bit-aliasing, uniqueness, reliability, steadiness, mean BER and stable-bit ratio with 95% confidence intervals and assessment badges](/images/blog/pufanalytics/metrics.webp)

**Analysis settings** apply to every view, and the report and reproduction script record them:

- **Enrolment reference.** *First read* (measurement 0) or *Majority vote* (the bitwise majority of all reads, a "golden" response).
- **Bootstrap B.** The number of bootstrap resamples for the confidence intervals. The default is 1,000; 0 turns them off.
- **CI level.** 90%, 95% or 99%.
- **NIST α.** The significance level of the randomness tests. The default is 0.01, as NIST recommends.
- **Bootstrap seed.** Makes the intervals reproducible.

Press **Recompute** after changing any of them.

The summary table gives each metric with its ideal value, interval and an assessment. Below it are bar charts per device and per bit position, plus the error rate of every bit position. For *k* devices with *n*-bit references *R<sub>i</sub>* and *T* re-reads *R<sub>i,t</sub>*:

$$
U_i = \frac{\mathrm{HW}(R_i)}{n}, \qquad
Q = \frac{2}{k(k-1)} \sum_{i<j} \frac{\mathrm{HD}(R_i, R_j)}{n}, \qquad
\mathrm{Rel}_i = 1 - \frac{1}{T}\sum_{t=1}^{T} \frac{\mathrm{HD}(R_i, R_{i,t})}{n}
$$

Here HW is the Hamming weight (number of 1s) and HD the Hamming distance (number of differing bits). **Steadiness** measures how consistently each cell of a device reads the same value. With *p<sub>i,l</sub>* the share of 1s that bit *l* of device *i* gives over its reads:

$$
S_i = 1 + \frac{1}{n}\sum_{l} \log_2 \max(p_{i,l},\, 1 - p_{i,l})
$$

**The confidence intervals resample devices, not bits.** The interval should describe what happens if you had built a different batch of chips, and the chip is the unit of variation. For uniqueness, a device paired with its own duplicate in a resample is skipped, so it cannot create artificial zero distances. The demo gives uniqueness **50.13%** with a 95% interval of 49.23 to 50.85, and reliability **99.54%** (99.44 to 99.64).

One historical note: PUFAnalytics versions before 2.0 returned uniqueness as *twice* the mean inter-device distance (ideal 1.0 instead of 0.5). Version 2.0 fixed this, and the changelog says so, because a value copied from an old version into a new paper would be wrong by a factor of two.

[Method notes: quality metrics](https://koustav.isroot.in/PUFAnalytics/#/docs/metrics). In Python, the `pufanalytics.quality` module has one function per metric.

### 3. Identification

Can a reader tell device A from device B, given one noisy read? This view treats the PUF like a biometric.

![The Identification view: decidability 11.61, empirical EER 0, binomial threshold 16 bits, FAR 2.49e-19, FRR 8.05e-20; intra- and inter-device distance histograms with dashed binomial fits; and the acceptance threshold explorer](/images/blog/pufanalytics/identification.webp)

The histogram puts the two distributions side by side. The **intra-device** distances (a device against its own re-reads) sit near zero. The **inter-device** distances (device against device) sit near 50%. The further apart they are, the easier identification is. Three numbers summarise the gap:

- **Decidability *d′*** is the distance between the two means, in units of their pooled spread: $d' = |\mu_\text{inter} - \mu_\text{intra}| \,/\, \sqrt{(\sigma^2_\text{inter} + \sigma^2_\text{intra})/2}$. Above about 6, errors are practically absent. The demo gives 11.61.
- **Empirical EER** is the equal error rate read directly off the measured distances.
- **Binomial FAR and FRR** model the distances as Binomial(*n*, *p*), with *p* fitted to each distribution.

A reader accepts a response when its distance to the enrolled one is at most *t* bits. Then the false-acceptance rate is FAR(*t*) = P(inter-distance ≤ *t*), and the false-rejection rate is FRR(*t*) = P(intra-distance > *t*). PUFAnalytics picks the **optimal threshold *t\**** that minimises the larger of the two.

The binomial model matters because measured data cannot show small error rates. The demo has 32 devices, so it has only 496 inter-device pairs, and the smallest non-zero FAR it could ever measure is about 1 in 500. The model extrapolates: at *t\** = 16 bits it gives FAR = 2.49 × 10<sup>−19</sup>.

Those tails are summed in log space, so they stay accurate below 10<sup>−300</sup> rather than rounding to zero. A χ² goodness-of-fit p-value appears next to each fit, so you can see whether the binomial assumption holds for your data. The chart below shows the model's main lesson for design: the error falls exponentially with response length.

<IdVsLength />

The **acceptance threshold explorer** has a slider for *t*. It shows the empirical and model FAR and FRR at the chosen threshold, and draws all four curves on a log axis. Further down are a **DET curve** (FRR against FAR, the standard biometric plot) and the **inter-device distance matrix**. A dark cell off the diagonal there means two devices that are suspiciously alike.

[Method notes: identification](https://koustav.isroot.in/PUFAnalytics/#/docs/identification). In Python: `stats.decidability()`, `stats.far_frr_curve()`, `stats.binomial_far_frr()`, `stats.binomial_fit()` and `stats.identification_vs_length()`.

### 4. Randomness & entropy

![The Randomness & entropy view: the NIST SP 800-22 table with p-values, a p-value bar, parameters and a pass/fail badge for each of eight tests, above a chart of Shannon and min-entropy per bit position](/images/blog/pufanalytics/randomness.webp)

The enrolled responses of all devices are joined into one bit stream and run through eight tests from **NIST SP 800-22**:

| Test | What it looks for | Minimum length |
|---|---|---|
| Frequency (monobit) | too many 1s or 0s overall | 100 bits |
| Block frequency | imbalance within blocks of *M* bits | 100 |
| Runs | too many or too few runs of identical bits | 100 |
| Longest run of ones | unusually long runs inside blocks | 128 |
| Cumulative sums | drift of the running ±1 sum (forward and backward) | 100 |
| Approximate entropy | over-frequent *m*-bit patterns | depends on *m* |
| Serial | uneven frequencies of all overlapping *m*-bit patterns (two p-values) | depends on *m* |
| Spectral (DFT) | periodic structure | 1,000 |

The implementations reproduce the worked examples in the NIST standard to six decimal places. The spectral test uses an exact DFT for any length, through Bluestein's algorithm, rather than padding to a power of two.

**A test that does not have enough data says *not applicable*.** It does not return a p-value, because a p-value from too little data looks like a result but is not one.

The demo fails one test: **Serial**, with p = 0.0037. That is worth reading closely rather than hiding. An Arbiter PUF's response is a linear function of its challenge features, so its responses to related challenges are not fully independent. One failure in eight at α = 0.01 is also not proof of anything by itself. Run the test on more data before drawing a conclusion.

The tiles above the table give five entropy estimates, plus a correlation figure:

- Shannon entropy and min-entropy per bit position, across the population;
- the **SP 800-90B Most Common Value** estimate (0.930 bits per bit for the demo);
- the **SP 800-90B Markov** estimate (0.970), which catches dependence between neighbouring bits;
- normalised **LZ76 complexity**, about 1 for random data;
- the mean absolute correlation between bit positions.

The charts below show entropy per bit position, the bit-position correlation matrix, and the autocorrelation of the responses with a 95% white-noise band.

[Method notes: randomness and entropy](https://koustav.isroot.in/PUFAnalytics/#/docs/randomness). In Python: `nist.run_all()` and the eight test functions, plus the `estimators` module.

### 6. Simulation studio

How does reliability change as noise grows? How many devices do you need before uniqueness settles? The simulation studio runs **Monte-Carlo sweeps** to find out.

![Simulation studio results for an SRAM PUF swept over noise sigma: uniformity, bit-aliasing spread, uniqueness and reliability against noise, each with a shaded 95% band](/images/blog/pufanalytics/simulation-studio.webp)

**To run a sweep:**

1. Pick a model and set the population: **Devices**, **Response bits** and **Repeats**.
2. Set **Seeds per point** and **First seed**.
3. Choose **Sweep parameter 1**, which becomes the x-axis. Any model parameter can be swept, and so can the population size, the response length or the number of repeats.
4. Enter its values in one of three forms:
   - a list, such as `0.01,0.05,0.1`;
   - a range, `start:stop:steps`, such as `0.02:0.5:8`;
   - a log range, `log:start:stop:steps`.
5. Optionally, choose a second parameter. That turns every metric into a 3D response surface.

Press **Run sweep**. The cost line shows how many simulations it will take.

Each grid point is simulated with every seed, and the result is the mean with a 95% band, mean ± 1.96·sd/√R for R seeds. The sweep uses **common random numbers**: replicate *r* gets seed *s*₀ + *r* at every grid point. Neighbouring points then differ only in the parameter, not in the luck of the draw, so the curves come out smooth with few seeds.

In the screenshot, SRAM reliability falls almost linearly from 100% to 80% as noise rises to 0.5, while uniqueness and uniformity do not move. Noise costs you reliability, not uniqueness.

**CSV** and **Python script** buttons export the sweep, and `pa.sweep()` runs the identical computation in Python. [Method notes: simulation studio](https://koustav.isroot.in/PUFAnalytics/#/docs/figures).

### 7. Attack lab

A PUF that a machine-learning model can predict is not a PUF. The attack lab runs the classic modelling attack: ridge-regularised logistic regression, fitted with Newton's method, on the challenge-parity features *φ*(*c*) of the additive delay model.

![The Attack lab: model tabs, stages, XOR values, noise, training and test CRP counts and seed, above a chart of held-out prediction accuracy against training set size for 1-, 2-, 3- and 4-XOR Arbiter PUFs](/images/blog/pufanalytics/attack-lab.webp)

**To run it:**

1. Pick **Arbiter / XOR**, **Feed-forward** or **Interpose (1,y)**.
2. Set the number of stages.
3. List the variants to compare: XOR widths, loop counts or *y* values, such as `1,2,3,4`.
4. Set the noise, the training set sizes and the test set size.
5. Press **Run attack**.

Each variant is a fresh simulated PUF, and the chart shows its accuracy on held-out challenges as the training set grows. With the defaults:

| PUF | 100 CRPs | 1,000 CRPs | 10,000 CRPs |
|---|---|---|---|
| 64-stage Arbiter (1-XOR) | 85.0% | 97.2% | **99.6%** |
| 2-XOR | 48.8% | 51.1% | 55.8% |
| 3-XOR | 51.8% | 53.0% | 54.3% |
| 4-XOR | 51.9% | 50.4% | 48.4% |

A plain Arbiter PUF is broken with a few thousand challenge-response pairs (CRPs). XOR versions stay near 50%, which is guessing, because XORing chains makes the problem non-linear in *φ* and this learner can only draw a straight boundary.

**This shows resistance to this attack only.** Neural networks, CMA-ES and reliability-based attacks do break XOR Arbiter PUFs, and the app's method notes say so.

Two more tools sit below the chart:

- **3D learnability landscape** plots accuracy over the number of stages and the training set size.
- **Attack your own CRPs** takes pasted `challenge,response` lines, or the active simulated Arbiter data set, and runs the same attack on your own data.

[Method notes: modelling attacks](https://koustav.isroot.in/PUFAnalytics/#/docs/attack). In Python: `attacks.simulated_attack()`, `attacks.modeling_attack()` and `attacks.logistic_regression()`.

### 8. Key generation

To turn a noisy PUF response into a stable cryptographic key, you need a **fuzzy extractor**. It combines an error-correcting code with *helper data* that is stored in public and lets the device repair its noisy read. The planner sizes one.

![The Key generation planner: bit error rate, min-entropy per bit, key length and target failure inputs filled from the dataset, tiles showing 11 of 22 configurations feasible with BCH(127,64,10) the most efficient at 381 PUF bits and 189 helper bits, and charts of key failure against PUF bits and against BER](/images/blog/pufanalytics/key-generation.webp)

**To use it:**

1. Enter four numbers: the **bit error rate** *p*, the **min-entropy per bit** *h*, the **key length** (64 to 256 bits) and the **target key failure** (10<sup>−3</sup> to 10<sup>−12</sup>).
2. When a data set is loaded, the form suggests its own values. Use the *worst* operating condition's BER for a conservative design.

The planner tries every combination of an inner repetition code (*r* = 1 to 15) and an outer block code (Hamming, Golay, Reed–Muller or BCH). It then lists the feasible ones, cheapest first. It uses the code-offset model:

$$
p_\text{in} = P\big[\mathrm{Bin}(r, p) > \lfloor r/2 \rfloor\big], \qquad
P_b = P\big[\mathrm{Bin}(n, p_\text{in}) > t\big], \qquad
P_\text{fail} = 1 - (1 - P_b)^{B}
$$

Each block of *nr* PUF bits leaks *nr* − *k* bits through the helper data, which leaves *nrh* − (*nr* − *k*) bits of entropy. The number of blocks *B* is chosen so that the leftover entropy covers the key.

For the demo, with a worst-case BER of 0.62%, *h* = 0.838 and a 128-bit key at 10<sup>−6</sup>, the winner is **BCH(127,64,10)** with no repetition. It needs 3 blocks, **381 PUF bits** and 189 helper bits, and its failure rate is 1.9 × 10<sup>−9</sup>.

![The 3D key-failure landscape for BCH(127,64,10): log key failure over bit error rate and repetition factor, above the table of configurations sorted by PUF bits](/images/blog/pufanalytics/key-landscape.webp)

The **cost vs failure** scatter plots every configuration, and the **BER sensitivity** curve shows how fast the selected design fails if the error rate drifts. The 3D landscape shows the same thing over BER and repetition at once. Click any row of the table to inspect it.

The model assumes independent bit errors and ignores decoder-specific and side-channel leakage. [Method notes: key generation](https://koustav.isroot.in/PUFAnalytics/#/docs/ecc). In Python: `ecc.plan_key_generation()`, `ecc.repetition_error()` and `ecc.block_failure()`.

### 9. Compare

Load or simulate two or more data sets, and **Compare** puts them side by side. Tick the data sets to include.

![The Compare view: checkboxes for two datasets, a radar chart of their quality fingerprints, a bar chart of quality index, and the start of a side-by-side metrics table](/images/blog/pufanalytics/compare.webp)

The radar overlays up to three data sets; more would no longer be readable in colour. The **quality index** bar chart and the **side-by-side table** show all selected data sets, and the table exports as CSV or LaTeX. The usual use is comparing designs (Arbiter against SRAM against RO) or batches (two wafers, two temperatures).

The quality index is the mean of seven normalised scores, which the radar also shows:

- uniformity;
- bit-aliasing;
- uniqueness;
- reliability;
- min-entropy;
- identifiability, from *d′*;

## Reproducibility: same seed, same bits

A simulated result is only reproducible if someone else can simulate the same population. Saying "we simulated 32 Arbiter PUFs with noise 0.06" is not enough, because a different random generator gives different chips, and different numbers. PUFAnalytics makes the seed the whole story:

<PaRngTape />

Two details make this hold across languages. xoshiro128\*\* uses only 32-bit integer operations, which JavaScript does exactly with `Math.imul` and `>>> 0`. And normal variates use only the cosine branch of Box–Muller, so every normal uses exactly two uniforms and the stream never goes out of step.

The proof is in the numbers. These are the demo population's results in the browser (from the screenshots above), next to the same population rebuilt in Python with `pa.simulate("arbiter", n_devices=32, n_bits=128, n_repeats=4, seed=2024, ...)`:

|---|---|---|
| Uniformity | 49.54% (CI 47.29–51.78) | 49.5361% (CI 47.2894–51.7822) |
| Uniqueness | 50.13% (CI 49.23–50.85) | 50.1276% (CI 49.2266–50.8494) |
| Reliability | 99.54% (CI 99.44–99.64) | 99.5361% (CI 99.4363–99.6404) |
| Decidability *d′* | 11.61 | 11.6054 |
| Binomial FAR at *t\** = 16 | 2.49 × 10<sup>−19</sup> | 2.4935 × 10<sup>−19</sup> |

## Using the Python package

```bash
pip install "git+https://github.com/TakMashhido/PUFAnalytics.git"
```

It needs Python 3.8 or newer and NumPy, nothing else. SciPy is only used by the test suite, to cross-check the special functions.

### Quick start

```python title="evaluate.py"
import pufanalytics as pa

# Real data: device,measurement,condition,response (binary or hex)
ds = pa.PUFDataset.from_file("measurements.csv")

# ...or the demo population from the web app, bit for bit
ds = pa.simulate("arbiter", n_devices=32, n_bits=128, n_repeats=4, seed=2024,
                 conditions=[("25C", 1.0), ("-40C", 1.8), ("85C", 2.6)],
                 stages=64, xor=1, noise=0.06)

result = pa.analyze(ds, reference="first", bootstrap=1000, seed=12345)
print(pa.to_markdown(result))           # readable report
pa.to_latex(result, "puf_table.tex")    # booktabs table for the paper
pa.to_json(result, "puf_full.json")     # every number, per device and per bit
```

`pa.analyze()` runs everything the web app's views show and returns a plain dictionary. Its main keys are `uniformity`, `uniqueness`, `reliability`, `ber`, `conditions`, `identification`, `entropy`, `nist`, `correlation` and `confidence_intervals`.

### Building blocks

Each analysis is also available on its own:

```python title="building_blocks.py"
from pufanalytics import quality, stats, nist, estimators, attacks, ecc
import pufanalytics as pa

quality.uniqueness(ds)                  # % (ideal 50)
quality.reliability(ds)                 # % per device
quality.bit_flip_rate(ds)               # per-bit error rate, for dark-bit masking
quality.condition_ber(ds)               # {'25C': {'ber': 0.0024, ...}, '85C': {'ber': 0.0062, ...}}
quality.tmv_ber(ds)                     # BER after temporal majority voting
nist.run_all(ds.reference().ravel())    # the eight SP 800-22 tests
estimators.markov_min_entropy(ds.reference().ravel())
stats.identification_vs_length(0.05, 0.5, [64, 128, 256])
pa.sweep("sram", "noise", [0.05, 0.1, 0.2], param2="n_bits", values2=[64, 128], seeds=5)
attacks.simulated_attack(stages=64, xor=2, train_sizes=(100, 1000, 10000))
ecc.plan_key_generation(ber=0.0062, min_entropy=0.838, key_bits=128, target_failure=1e-6)
```

### Command line

Installing the package also installs a `pufanalytics` command:

| Command | What it does |
|---|---|
| `pufanalytics simulate MODEL -o out.csv` | Simulate a population. Options: `--devices`, `--bits`, `--repeats`, `--seed`, `--conditions 25C:1,85C:2.5` and repeatable `--param key=value` (such as `--param xor=2`). Writes `.csv` or `.json`. |
| `pufanalytics analyze FILE` | Run the full evaluation. Options: `--markdown`, `--latex` and `--json` to save reports, `--reference first\|majority`, `--bootstrap`, `--seed`, `--no-nist` and `--format auto\|bin\|hex`. |
| `pufanalytics nist FILE` | Print the SP 800-22 results for the enrolled responses (`--alpha`, `--reference`). |
| `pufanalytics attack` | Logistic-regression learning curve on a simulated Arbiter PUF (`--stages`, `--xor`, `--noise`, `--train-sizes`, `--test-size`, `--seed`). |
| `pufanalytics ecc --ber P` | Fuzzy-extractor plans (`--min-entropy`, `--key-bits`, `--target`, `--top`). |

```bash title="terminal"
pufanalytics simulate sram -o sram.csv --devices 50 --bits 256 --conditions 25C:1,85C:2.5 --param bias=0.1
pufanalytics analyze sram.csv --markdown report.md --latex table.tex --json full.json
pufanalytics ecc --ber 0.0062 --min-entropy 0.838 --key-bits 128 --target 1e-6
```

## How it is tested

- **NIST worked examples.** Each SP 800-22 test reproduces the example sequences and p-values printed in the standard, to six decimal places.
- **SciPy cross-checks.** The incomplete gamma functions, normal CDF and binomial tails are compared against SciPy to about 10<sup>−12</sup> relative error, including far tails.
- **Cross-language parity.** The over 2,400 values in `golden.json`, from Python, must be reproduced by the browser engine: simulated populations bit for bit, and statistics to floating-point tolerance.
- **Continuous integration** runs the pytest suite and the parity test on every push. A separate workflow deploys the web app to GitHub Pages.

```bash title="terminal"
pytest -q                          # Python test suite
python tests/make_golden.py        # regenerate reference values from Python
node web/tests/parity.test.mjs     # the browser engine must match them
```

## What it does not do

- **It assumes independent bit errors** in the binomial identification model and in the key planner. Real PUFs often have correlated errors, for example cells that fail together when hot. Check the χ² fit p-value; when it is tiny, trust the empirical curves more than the extrapolated ones.
- **A resisted attack is not a security proof.** The attack lab runs one classic learner. It is useful for showing *why* XOR helps, and useless for claiming that something is secure.
- **The quality index is a heuristic.** It helps you compare designs at a glance. Do not put it in a paper as a metric.
- **The simulators are models**, not silicon. They are good for intuition, for checking the pipeline, and for "what if" sweeps. They do not replace measuring real chips.
